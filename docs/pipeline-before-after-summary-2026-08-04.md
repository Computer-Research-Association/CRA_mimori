## 0. 한 줄 요약

**이전**: 크롤러 5개가 각자 다른 방식으로 데이터를 모으고, 정제는 최소한만 하고, 관련성 판정도 없이 그대로 임베딩했다. 품질을 "측정"할 방법 자체가 없었다.

**이후**: 크롤링 정확도(정렬/쿼리 다각화), 정제 완성도(UI상투어 실제 제거), 문서 단위 관련성 판정(judge), 임베딩 품질(컨텍스트/중복제거) 네 층을 전부 손봤고, 그 효과를 매번 실측(fixture 기반 before/after)으로 검증했다. 동시에 **리터럴 매칭이라는 핵심 설계의 구조적 한계**도 여러 번 실제로 드러났다.

## 1. 크롤링 단계

### 이전
- dcinside: 정렬 accuracy 하나만
- natepann: 정렬 HD(인기) 하나만
- tavily: 쿼리 `"{키워드}" 뜻 유래 밈 인터넷 커뮤니티` 하나만. 네이버 블로그 미러링(m./PC, PostView 쿼리형식) 중복 미제거. 구글 리다이렉트 스니펫(`/goto?url=...`) 미필터.
- youtube: 쿼리 relevance 하나만
- namuwiki: 특정 문서 그대로(정렬 개념 없음)
- 소스 4개(youtube 제외 요청 안 됐지만 실질 5개 소스), 관련성 게이트는 부분 문자열 매칭 하나로 통일

### 이후
- **natepann**: 인기(HD)+최신(DD) 조합, 예산 반씩 분배
- **dcinside**: 정확도(accuracy)+최신(latest) 조합
- **tavily**: 현재 쿼리+키워드 단독 쿼리 조합. 네이버 미러링 canonical key(`blogId::logNo`) 기준 배치 내 중복 제거. 스킴 없는 리다이렉트 URL 필터.
- **신규 소스 추가**: 오늘의유머(todayhumor.co.kr) — robots.txt 확인 후(일반 봇 `Allow: /`, `search=yes`) 제목 검색 크롤러 구현. 댓글은 JS로 사후 로딩돼 정적 스크래핑 불가라 본문만 수집.
- **후보였지만 보류/제외**: 펨코·클리앙·엠엘비파크(robots.txt가 검색 자체를 정책상 차단), 개드립·인스티즈(검색 결과가 JS/AJAX 렌더링이라 정적 스크래핑 불가, 헤드리스 브라우저 필요 — 별도 결정 필요), youtube 정렬 조합(API 쿼터 소진으로 검증 자체 못 함)

### 의의
- **실측으로 확인**: natepann/dcinside 정렬 간 겹침이 사실상 0%(세 정렬 모두 겹친 문서 0건) — 조합이 실제로 커버리지를 넓힌다는 게 가설이 아니라 데이터로 확인됨.
- **tavily 쿼리 다각화 효과 확인**: 현재 쿼리는 언론기사급 고품질 설명 콘텐츠를, 단독 쿼리는 커뮤니티 질문·소셜 게시물을 각각 더 잘 찾음(교집합 8~17%뿐).
- **robots.txt를 먼저 확인하고 판단한 것 자체가 의의**: ClaudeBot을 이름으로 명시한 차단, 검색 경로만 별도 차단 등 실제 정책을 읽고 후보를 걸러냈다(추측 아님).

### 한계
- **개드립/인스티즈는 여전히 크롤링 불가** — JS 렌더링 문제, 헤드리스 브라우저 도입이라는 더 큰 결정이 필요.
- **youtube 정렬 조합은 검증도 못 한 상태**(API 쿼터 소진). 프로덕션에서 이미 쿼터가 빠듯할 수 있다는 신호.
- **크롤러의 예외 처리가 뭉뚱그려져 있음** — Mongo 연결 실패와 진짜 중복 키 에러를 구분 안 하고 전부 "중복"으로 표시. 오늘 밤 직접 이 버그에 걸려 30분을 허비했다(원인: `.env`의 도커 내부 호스트명이 호스트 실행 시 해석 안 됨). 아직 코드로 안 고침.
- **tavily 날짜 컷오프는 포기함** — `published_date`가 애초에 거의 없어(298건 중 0건) 기술적으로 실효성이 없었음.

## 2. 정제(cleaner) 단계

### 이전
HTML 태그/엔티티, URL, 이메일·전화번호, 반복문자만 처리. UI 상투어는 `quality_test/signals.py`가 개수만 세고 실제로 지우지 않음.

### 이후
`config.BOILERPLATE_PHRASES`(네이버 블로그 12개 + 다음 카페 18개, 실제 오염 사례에서 추출)를 `cleaner.py`가 실제로 제거. 탐지 목록(signals.py)과 제거 목록이 같은 config 상수를 공유해 기준이 어긋나지 않음.

### 의의
- 실사례 999문서 기준 **UI 상투어 포함 청크 161건 → 0건**(완전 제거).
- 상투어 제거로 청크 경계가 재계산되면서, 예전엔 상투어에 가려 짧게 잘렸던 청크가 실제 본문까지 더 담게 되는 부수 효과도 확인.

### 한계
- **목록 기반 방식이라 새 사이트마다 계속 추가해야 함** — 오늘 밤도 다음 카페 사례를 사용자가 직접 짚어줘서 발견하고 추가함. 일반화 어려운 표현(사이트 고유 마스코트 이름, 방문자 수 등)은 의도적으로 안 넣음.
- **스팸 실제 제거가 아니라 청크 통째 드롭** — 부분 삭제(surgical removal)가 아니라서, 정상 내용과 스팸이 한 청크에 섞여 있으면 정상 내용까지 같이 사라질 수 있음(다만 본문/댓글 분리 이후로는 스팸이 대개 댓글 청크에 격리돼 위험이 낮아짐).

## 3. 청킹(chunker) 단계

### 이전
- "[댓글]" 마커를 구분자 **우선순위**로만 넣어서, 본문+댓글 합계가 500자(CHUNK_SIZE) 안이면 **아예 안 갈라짐** — 로직 결함.
- 최소 길이 10자.
- 스팸 필터 없음.

### 이후
- "[댓글]" 마커로 **항상 먼저** 분리 후 각각 독립 재귀분할. `content_type` 필드(body/comment) 부여.
- 최소 길이 30자.
- 스팸 청크(`spam_hits>=3`) 통째 드롭.

### 의의
- 실사례로 확인: 예전엔 본문 키워드 덕에 "매치"로 잘못 표시되던 통짜 청크가, 분리 후엔 댓글 부분이 정직하게 "미매치"로 나옴 — 신호 왜곡이 사라짐.
- **재현율 우선 원칙과 충돌 지점을 사용자가 직접 판단**: 30자 미만이라 문서가 통째로 사라지는 부작용(185건, 표본 조사 결과 상당수는 진짜 잡담이지만 일부는 실제 사용례) — 본문+댓글 합산 길이 예외 도입 여부를 검토했으나 **사용자가 "개별 30자 기준 유지"로 최종 결정**.

### 한계
- 위 185건 소멸 이슈는 "해결"이 아니라 "현 상태 유지로 결정"됨 — 짧은 실제 사용례 손실은 여전히 존재.
- 최소 길이/스팸 임계값(30자, 3건)은 1단계에서 데이터 분포 보고 잡은 시작값이지, 정식 라벨셋으로 검증된 값은 아님.

## 4. judge — 문서 단위 관련성 판정 (완전 신규)

### 이전
없음. `feature/rag_test` 브랜치에 유사 기능이 있었으나 dev에 머지 안 됨(오래된 브랜치라 그대로 머지하면 다른 최신 기능이 되돌아감).

### 이후
`preprocessing/pipeline.py`의 `process_one()`이 `quality_test.matching.find_keyword`(1단계에서 만든 정규화 단일 정의)를 재사용해 문서 전체(clean_content, 청킹 이전 전문) 기준으로 한 번 판정 → 모든 청크에 `is_relevant`/`relevance_position`/`relevance_match_count` 동일하게 부착.

### 의의
- **tavily 표본 검증에서 15/15 정확** — 실제로 "밈이 뭔지 설명하는" 범용 위키/블로그를 정확히 걸러냄.
- **진짜 버그를 사용자 요청으로 발견·수정**: 처음엔 "살아남은 청크만 이어붙여" 판정했는데, 청킹 필터(30자 미만 드롭)가 키워드 든 짧은 본문을 지우면 증거가 사라져 오판하는 문제 발견 → `clean_content`(청킹 이전 전문) 기준으로 수정. 수정 후 dcinside 오판 36건→2건.
- 오염의 실제 분포를 재확인: 예전 라벨셋 근거로 "natepann이 오염 대부분"이라 알고 있었는데, 실측으론 **tavily가 대부분**(19.8%) — 낡은 라벨셋 근거를 정정.

### 한계
- **"67" 문제**: 숫자/극도로 일반적인 키워드는 리터럴 매칭이 원천적으로 무력함. "67승", "670만" 같은 무관한 등장도 전부 매치로 판정됨 — dcinside/natepann/todayhumor 전부 이 문제를 겪음(tavily만 쿼리 문맥 덕에 우연히 무사).
- **"뭔말알"류 축약 키워드**: 실제 게시글은 "뭔 말인지 알거같음"처럼 풀어서 쓰는데 축약형 리터럴은 그 안에서 연속 문자열로 안 나와서 못 잡음(natepann에서 확인).
- **비한국어 콘텐츠**: 내용은 정확한데 언어가 다른 경우(중국어 사례) 어떻게 다룰지 미정 — 표본 부족으로 판단 보류.
- **판정만 하고 임베딩 자체는 안 막음** — 아래 §5 참고.
- 사람 라벨 100건 정식 검증은 자동화 불가라 미완료.

## 5. judge를 실제로 "쓰는" 단계 (RAG 검색 시점 필터)

### 이전
judge 자체가 없었으니 당연히 없음.

### 이후
`analysis/rag_pipeline.py`의 `_is_valid_chunk()`에 `is_relevant is False`면 제외하는 조건 추가. **벡터/저장은 안 건드리고 검색 결과에서만 제외** — is_relevant 필드가 없는(judge 이전) 기존 데이터는 `None`과 `False`를 구분해 회귀 없이 통과.

### 의의
가장 되돌리기 쉬운 지점에 필터를 걸었다 — judge 정확도에 문제가 생겨도 임베딩을 다시 할 필요 없이 이 조건 하나만 되돌리면 즉시 원복됨.

### 한계
- **비관련으로 걸러진 문서도 여전히 임베딩·저장은 됨** — 벡터DB 용량/임베딩 비용은 그대로 쓴다. "아예 임베딩을 안 한다"는 더 공격적인 옵션은 되돌리기 어려워서(재처리 트리거가 있어도 완전한 원복은 아님) 의도적으로 안 했음.

## 6. 임베딩 단계

### 이전
- 나무위키 섹션 청크도 `text`만 인코딩(섹션 제목 문맥 없음).
- 근접중복 제거 없음 — RAG가 질의마다 반복 계산(`analysis/langchain_playground.ipynb`의 difflib 방식).
- 재처리 트리거 없음 — `is_embedded`를 되돌리는 코드가 아예 없어서, 오늘 밤 개선한 로직이 기존 임베딩 데이터엔 절대 소급 적용 안 됨.

### 이후
- `_encoding_text()`: `section_title` 있는 청크(나무위키)는 제목+섹션제목을 앞에 붙여 인코딩(저장 텍스트는 그대로 유지).
- `_filter_near_duplicates()` + `_fetch_existing_texts()`: 같은 키워드의 기존 청크 + 같은 배치 내 청크와 근접중복(문자 유사도 0.8) 검사, 적재 시점에 한 번만 제거.
- `reset_for_reprocessing()` + `reprocess_trigger_main.py`: `is_embedded`를 다시 `False`로 되돌려 재처리 대상에 포함. keyword/source 중 하나는 필수(전체 재처리 사고 방지).

### 의의
- 근접중복 제거를 **RAG 질의마다 반복 계산하던 것에서 적재 시점 1회로 이동** — 이후 모든 질의가 이 계산을 다시 안 해도 됨.
- 재처리 트리거가 생김으로써, 오늘 밤 만든 모든 개선(judge, 청킹, 정제)이 **기존 데이터에도 소급 적용될 길이 열림**(트리거 실행 전까지는 새 문서에만 적용).

### 한계
- 근접중복 비교는 키워드당 최대 500건까지만(scroll 페이지네이션 없음) — 그 이상 쌓인 키워드는 오래된 청크와는 비교 안 함.
- 재처리 트리거는 "표시만 되돌리는 것"이지 실행이 아님 — 실제 재처리는 다음 스케줄러 실행을 기다려야 함.

## 7. 종합 — 오늘 밤 작업의 의의

1. **측정 없이 개선은 없다는 원칙을 끝까지 지킴** — 모든 변경을 fixture 기반 before/after로 실측했고, "좋아진 것 같다"가 아니라 숫자와 실제 문서로 확인함.
2. **실제 버그 2건을 재현·수정**: RAG 정규화 드리프트("거제 야호~" 탈락), judge의 clean_content 미사용 버그. 둘 다 "있을 것 같다"가 아니라 실측 중에 우연히/의도적으로 발견함.
3. **사람이 판단해야 하는 지점을 코드로 대신 결정하지 않음** — 185건 소멸, 비한국어 콘텐츠, "67" 문제 전부 사용자에게 사실과 트레이드오프만 제시하고 최종 판단은 넘김.
4. **정책(robots.txt) 확인을 코딩보다 먼저 함** — 새 크롤러 후보 6곳을 실제로 확인하고 3곳은 정책상 제외, 2곳은 기술적 한계로 보류.
