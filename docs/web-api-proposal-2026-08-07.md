# 웹 API 서버 도입 제안 (PM 보고용)

**2026-08-07 / 대상: 프로젝트 관리자 / 작성 근거: `docs/superpowers/specs/2026-08-07-ec2-web-api-design.md`**

> **한 줄 요약** — 데이터 파이프라인은 EC2에서 매일 정상 가동 중이지만 **외부에서 그 결과를 꺼내 갈 통로가 하나도 없습니다.** 이번 작업은 웹사이트를 만드는 게 아니라, 웹사이트가 붙을 수 있는 **접점(HTTP API) 3개를 여는 것**이고, 기존 파이프라인은 손대지 않습니다.

---

## 1. 왜 지금 필요한가

현재 EC2(`100.29.36.216`)에서는 크롤링 → 전처리 → 임베딩 → 트렌드 판정 파이프라인이 스케줄러로 상시 자동 실행되고 있습니다. 데이터도, 분석 기능(RAG 질의응답 / 밈 분석 / 트렌드 판정)도 이미 완성되어 동작합니다. **문제는 이 기능들이 전부 "터미널에서 사람이 직접 실행하는 프로그램" 형태라는 점입니다.** 브라우저가 인터넷으로 요청을 보내 결과를 받아 갈 방법이 존재하지 않습니다.

확인 과정에서 드러난 사실 하나를 그대로 보고드립니다. `docker-compose.yml`에는 `flask`라는 이름의 서비스가 이미 등록되어 있어 웹 서버가 있는 것처럼 보이지만, **코드베이스 전체에 `Flask(...)`나 `@app.route`가 단 한 줄도 없습니다.** 그 서비스가 실제로 실행하는 것은 크롤링 스케줄러입니다. 즉 웹 서버는 이름만 있고 실체가 만들어진 적이 없습니다.

그래서 지금은 프론트엔드 개발을 시작하려 해도 **붙일 대상이 없는 상태**입니다. 이 작업은 웹사이트 개발의 선행 조건이며, 이것이 없으면 프론트 일정은 착수 자체가 불가능합니다.

---

## 2. 무엇을 만드는가 (제작 형태)

기존 함수는 그대로 두고, 그 앞에 **HTTP로 호출 가능한 문**만 답니다.

| 엔드포인트 | 웹사이트가 보내는 것 | 돌려받는 것 |
|---|---|---|
| `POST /api/rag` | 키워드 + 질문 | 답변 + 출처 링크 목록 + 트렌드 |
| `POST /api/analyze` | 키워드 | 뜻·유래·뉘앙스 분석 텍스트 + 트렌드 |
| `GET /api/trend/<키워드>` | 키워드 | 유행 상태(핫함/유행 중/감소 등) |
| `GET /api/keywords` | – | 조회 가능한 키워드 목록 |
| `GET /api/health` | – | 서버 생존 확인(모니터링·배포 검증용) |

배포 구조는 컨테이너 서비스가 3개에서 4개로 늘어나는 것뿐입니다.

```
현재:  flask(실제로는 스케줄러) / mongo / qdrant
변경:  scheduler(이름 정리) / api(신규) / mongo / qdrant
```

---

## 3. 왜 이런 형식으로 만드는가

각 설계 판단과 그로 인해 **회사·서비스 입장에서 달라지는 것**을 함께 적었습니다.

**① 기존 파이프라인을 재작성하지 않고 그대로 재사용합니다.**
RAG·분석·트렌드 로직(`analysis/`, `trend/`, `embedding/`)은 수정 없이 호출만 합니다. 신규 파일은 `api/app.py`, `api/routes.py` 2개뿐이고, 기존 코드 수정은 딱 2곳(트렌드 캐시 조회 함수 추가, 프롬프트 생성 함수에 선택 인자 1개 추가 — 둘 다 기존 동작을 바꾸지 않는 하위호환 변경)입니다.
→ **매일 돌고 있는 데이터 수집 파이프라인이 이번 작업으로 깨질 여지가 구조적으로 거의 없습니다.**

**② 스케줄러와 API를 별도 서비스로 분리합니다.**
API 서버가 트래픽이나 메모리 문제로 죽어도, 크롤링·임베딩 스케줄러는 별개 컨테이너라 영향을 받지 않습니다.
→ **웹서비스 장애가 데이터 자산 축적 중단으로 번지지 않습니다.** 이번 설계에서 가장 중요한 한 가지를 꼽으라면 이것입니다.

**③ 트렌드 조회는 실시간 외부 호출 대신 DB에 저장된 값을 읽습니다.**
트렌드 판정은 네이버·카카오·구글을 조회하는데, 구글 쪽은 비공식 경로라 자주 차단됩니다. 방문자가 조회할 때마다 실시간 호출하면 **우리 EC2의 IP 자체가 차단당할 수 있고, 그 피해는 API가 아니라 매일 돌던 기존 파이프라인이 받습니다.** 다행히 크롤 사이클(2시간)마다 판정 결과를 `trend_scores` 컬렉션에 이미 저장하고 있어, 그 값을 읽기만 하면 됩니다.
→ **더 빠르고(외부 대기 없음), 기존 자산을 위험에 빠뜨리지 않습니다.**

**④ 개발용 내장 서버가 아니라 운영용 서버(gunicorn)로 띄우고, 동시 처리량에 상한을 둡니다.**
Flask 기본 서버는 공식 문서가 "운영 환경에 쓰지 말 것"이라고 명시한 개발용이며, 요청을 한 번에 하나씩만 처리합니다. 운영용 gunicorn으로 실행하되, 이 EC2는 GPU 없는 CPU 인스턴스이고 질문 임베딩(BGE-M3)이 무겁기 때문에 **동시 처리는 2건으로 제한**하고 초과분은 즉시 "잠시 후 다시 시도" 응답을 돌려줍니다. 또 답변 생성(외부 LLM)이 재시도 포함 수 분 걸릴 수 있어 타임아웃을 300초로 넉넉히 잡습니다.
→ **한 번에 몰린 요청이 mongo·qdrant·크롤러까지 끌어내려 전체 서비스를 마비시키는 상황을 코드 차원에서 차단합니다.**

**⑤ 방화벽은 API 포트 하나만 엽니다.**
`docker-compose.yml`에는 mongo(27017), qdrant(6333/16333) 포트도 노출 설정이 있고, 지금 안전한 이유는 AWS 보안그룹이 이를 막고 있기 때문입니다. 우리 mongo에는 비밀번호가 걸려 있지 않아, 실수로 함께 열리면 누구나 데이터를 읽고 삭제할 수 있습니다.
→ **이번에 5000 포트만 추가로 열고, DB 포트는 계속 닫힌 상태인지 배포 시 명시적으로 재확인하는 절차를 넣었습니다.**

## 4. 현재 설계의 한계 (사전 공유)

과장 없이 먼저 말씀드립니다. 아래는 결함이 아니라 **현 인프라 규모에서 의도적으로 감수한 트레이드오프**입니다.

- **동시 2건 상한** — 초과 요청은 즉시 거절(재시도 안내)됩니다. 소규모 시연·내부 테스트·프론트 개발에는 충분하지만, **대외 홍보나 런칭성 트래픽은 이 구성으로 감당할 수 없습니다.** 그 시점에는 인스턴스 증설이 선행되어야 합니다.
- **응답이 느릴 수 있음** — 답변 생성이 외부 LLM 호출이라 수 초~수 분까지 편차가 있습니다. 프론트는 로딩 UI를 전제로 설계해야 합니다.
- **인증·사용량 제한 없음** — 현재는 누구나 호출 가능한 구조입니다. 따라서 **서버 IP를 대외에 공개하지 않는 것을 전제로 운영**해야 하며, 공개 시점 전에 5번 항목의 보완이 필요합니다.

---

## 5. 이번 범위에서 의도적으로 제외한 것

오해 방지를 위해, 빠진 것이 아니라 **미룬 결정**임을 명시합니다.

| 항목 | 이번에 뺀 이유 | 다시 논의할 시점 |
|---|---|---|
| 도메인 + HTTPS | 아직 도메인 미보유. 당장은 IP 직접 접속으로 충분 | 도메인 구매 확정 시 |
| API 키 / 사용량 제한 | 외부 미공개 전제라 우선순위 낮음 | **서비스를 대외 공개하기 전 (필수 선행)** |
| CORS 도메인 제한 | 프론트 주소가 아직 없어 전체 허용으로 시작 | 프론트 도메인 확정 시 |
| 프론트엔드(웹사이트) | 이 작업의 후속. API가 있어야 착수 가능 | 본 작업 완료 직후 |

---

## 6. 요청 사항 (승인·확인 필요)

1. **AWS 보안그룹 인바운드에 5000 포트(TCP) 추가 개방 승인** — API 접속에 필수.
2. **동일 작업 시 27017 / 6333 / 16333 포트가 함께 열리지 않는지 확인** — 인증 없는 DB 노출 방지.
3. **EC2 반영 시점 승인** — 이번 개발 범위는 로컬 구현·검증까지이며, EC2 배포는 별도 승인 후 진행합니다.
4. **프론트엔드 도메인이 확정되면 공유 요청** — CORS 범위 축소와 HTTPS 도입 논의를 그때 시작합니다.
