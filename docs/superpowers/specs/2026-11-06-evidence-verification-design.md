# 분석 경험 및 근거 갱신 설계

## 의도

새 단어 분석을 요청한 사용자가 현재 처리 단계와 예상 대기 범위를 이해하고, 같은 단어를 다시 요청해도 기존 작업을 계속 볼 수 있게 한다. 분석 결과는 새로 수집한 자료가 기존 답변을 바꿀 만큼 관련 있고 새로운 경우에만 갱신한다. 답변 아래에는 생성일이 아닌 마지막 근거 검토의 결과를 표시한다.

## 목표

- 신규 수집 작업에 `대기`, `관련 자료 수집`, `내용 정리`, `답변 생성`의 이해 가능한 상태를 제공한다.
- 새 단어의 크롤링 상태 API가 대기열 위치와 최근 완료 작업을 바탕으로 한 **범위형** 예상 시간을 제공한다. 정확한 완료 시각을 약속하지 않는다.
- 같은 키워드의 대기·실행 작업은 하나만 유지하고, 재방문 및 중복 요청은 그 작업의 현재 상태를 반환한다.
- 브라우저를 떠났다가 돌아와도 서버 작업이 계속되며, 해당 키워드를 다시 선택하면 기존 상태 또는 완료 결과를 다시 표시한다.
- 새 임베딩은 완료 답변을 즉시 지우지 않는다. 새 자료가 독립 URL 수와 관련도 기준을 만족할 때만 기존 분석을 재생성 큐로 전환한다.
- 결과 하단에는 다음 중 하나만 표시한다.
  - `근거 검증 기준일 · YYYY. MM. DD` + `이후 수집된 자료를 확인했지만, 답변을 바꿀 만큼 의미 있는 내용 변화는 없습니다.`
  - `근거 검증 기준일 · YYYY. MM. DD` + `새 근거를 반영해 분석을 갱신했습니다.`
- 근거가 부족하면 단정 대신 초기 사용례 중심이라는 안내를 유지·명확화한다.
- 상위 근거는 동일 URL·근접 중복을 제외하고, 한 출처가 결과를 독점하지 않게 선택한다. 독립 자료가 부족하면 상한을 강제해 근거 수를 줄이지 않는다.

## 비목표

- 답변마다 별도 LLM 사실검증 호출을 추가하지 않는다.
- 기존 화면의 시각 디자인이나 페이지 구조를 재설계하지 않는다.
- `.env`, MongoDB, Qdrant의 실제 운영 데이터를 수동으로 변경하거나 노출하지 않는다.
- NIM 장애 정책과 내부 평가 대시보드는 이번 사용자 화면 개선 범위에서 제외한다.

## 동작

1. 새 단어 요청 API는 같은 키워드의 활성 작업이 있으면 이를 재사용한다. 상태 응답은 `queue_position`, `estimated_wait_seconds`, 사용자용 `display_stage`를 포함한다.
2. 크롤링 워커는 기존 기술 단계(crawl, preprocess, embed)를 계속 기록한다. API는 이를 사용자 문구로 변환한다.
3. 완료 후 단어를 다시 선택하면 기존 분석 요청·결과를 재사용한다. 새 브라우저 세션은 서버에서 키워드별 활성 작업을 찾아 복원한다.
4. 임베딩 완료 시 영향을 받은 키워드를 검증 후보로 기록한다. 무조건 완료 분석 캐시를 삭제하는 동작은 제거한다.
5. 검증 워커는 새 근거의 URL 다양성과 검색 관련도를 검사한다. 기준 미달이면 답변은 보존하고 `unchanged` 상태와 검토 시각만 기록한다. 기준 통과면 기존 LLM 생성 큐를 이용해 답변을 갱신하고 `updated` 상태를 저장한다. 별도 LLM 판정 호출은 하지 않는다.
6. API와 `AnalysisPanel`은 검증 메타데이터를 전달·표시한다. 메타데이터가 없는 기존 결과는 기존 표시를 유지한다.

## 제약

- 기존 수동 분석, 신규 키워드 온디맨드 수집, 출처 필터별 캐시 키 동작을 보존한다.
- 예상 시간은 서버의 최근 처리 기록이 없으면 보수적인 범위 문구를 사용한다.
- 출처 제한은 강제 삭제가 아니라 중복 감점 및 우선순위 조정이다.
- 모든 사용자 문구는 한국어로 제공한다.
