# RAG 파이프라인 개선 노트 (크롤러 / 청킹 / 임베딩)

`analysis/langchain_playground.ipynb`에서 RAG 답변 품질 실험을 진행하며 발견한, **크롤러 →
전처리(청킹) → 임베딩** 단계에 걸친 개선점 정리입니다. RAG 쪽(`analysis/rag_pipeline.py`)에는
이미 대응 필터를 넣어뒀지만, 전부 "증상 완화"용 임시방편이라 근본 해결은 데이터가 만들어지는
앞단(이 문서에서 다루는 단계들)에서 이뤄져야 합니다.

크롤러 오염 사례(키워드 태깅 오류, 날짜 필터 폴백 구멍)는 이미 `docs/crawler-contamination-findings.md`에
자세히 정리돼 있으니 그쪽을 참고하시고, 이 문서는 **그 이후에 추가로 발견한 것 + 청킹/임베딩 단계**를 다룹니다.

---

## 1. 크롤러 — 추가로 발견한 것

### 1.1 tavily 검색 쿼리 설계가 SEO 콘텐츠 팜을 그대로 낚음

`crawlers/tavily_crawler.py`:
```python
query = f"{keyword} 뜻 유래 밈 인터넷 커뮤니티"
```
이 쿼리 문구가 정확히 SEO 블로그들이 "[키워드] 뜻 유래"라는 제목으로 글을 쓰는 이유 그 자체입니다.
"야르" 실험에서 tavily로 열었더니, `blog.naver.com`, `tistory.com`, `pandarank.net`(블로그 SEO
분석 도구 사이트) 등에서 나온 "설명형" 글이 대거 잡혔는데:
- 기원 설명이 **블로그마다 서로 모순**됨 (하나는 "2000년대 유행어", 하나는 "일본어 동사 やる
  그대로", 하나는 "BJ 리액션에서 시작") — 근거 없이 각자 그럴듯한 기원을 지어낸 것으로 보임
- 이건 관련성 필터(길이/키워드/dense)로는 못 잡습니다 — 오히려 키워드를 반복적으로 잘 써놔서
  필터를 더 잘 통과합니다

**제안**: 쿼리 문구 자체를 재검토(예: "커뮤니티 반응" 쪽에 더 가중치를 주는 쿼리로 변경), 또는
알려진 SEO 콘텐츠 팜/블로그 랭킹 도구 도메인(`pandarank.net` 등)을 블랙리스트 처리.

### 1.2 네이버 블로그 미러링으로 인한 중복 수집

같은 글이 `in.naver.com/{author}/contents/internal/{id}`와 `blog.naver.com/{author}/{id}`
두 URL에 동일 내용으로 존재하는 사례를 확인했습니다(네이버 블로그의 "인플루언서" 플랫폼과 개인
블로그 플랫폼 간 미러링으로 추정). 크롤러는 이걸 서로 다른 문서로 저장해서, 같은 정보가 여러
"출처"로 부풀려져 인용될 위험이 있습니다.

**제안**: 크롤링/저장 시점에 URL host를 정규화(`in.naver.com`/`blog.naver.com`을 같은 것으로
취급)하거나, 콘텐츠 해시 기반으로 사전에 걸러내는 로직 추가.

### 1.3 검색결과 스니펫이 실제 페이지처럼 저장된 사례

`title`이 `"...가 절로 나오는 대학생활 순간 이 ..."`처럼 **말줄임표로 끝난 채** 저장되고,
`url`이 `/goto?url=CAESxxxx...`(검색엔진 리다이렉트/트래킹 URL) 형태인 항목을 발견했습니다.
실제 페이지를 크롤링한 게 아니라 검색결과 카드의 스니펫 텍스트를 그대로 캡처한 것으로 보입니다.

**제안**: 저장 전에 `title`이 "..."로 끝나는지, `url`이 실제 도메인이 아니라 리다이렉트 패턴인지
감지해서 걸러내거나, 리다이렉트를 실제 목적지로 resolve.

## 2. 청킹 — `preprocessing/chunker.py`, `preprocessing/cleaner.py`

### 2.1 청크 최소 길이 필터가 너무 낮음 (10자)

`chunker.py:81`:
```python
if len(chunk_text.strip()) < 10:  # 노이즈 청크 제거
    continue
```
**10자**는 "야르\n- dc official App"(13자) 같은 정보 없는 한 줄짜리를 못 거릅니다. 이것 때문에
RAG 쪽(`analysis/rag_pipeline.py`)에서 별도로 30자 기준 필터를 다시 넣어야 했습니다. 청킹
단계에서 한 번 제대로 걸러지면, Qdrant에 애초에 안 쌓이니 저장공간도 아끼고 모든 쿼리가 혜택을 봅니다.

**제안**: 이 임계값을 20~30자 수준으로 올리는 것을 검토 (단, "67"처럼 원래 짧은 키워드 자체가
본문인 경우는 예외 처리 필요할 수 있음 — 실데이터로 튜닝 권장).

### 2.2 본문/댓글 분리가 "문서 전체 길이"에 좌우됨

`chunker.py`의 스플리터는 `separators=["\n\n[댓글]\n", "\n\n", "\n", ". ", " ", ""]`로
"[댓글]" 경계를 우선 분리하려고 시도하지만, **`RecursiveCharacterTextSplitter`는 전체 텍스트가
`CHUNK_SIZE`(500자, `config_cilent.py:56`)를 넘지 않으면 아예 분할을 안 합니다.** 그래서 짧은
게시글 + 긴 댓글(특히 스팸 광고 댓글)이 합쳐진 길이가 500자를 안 넘으면, 본문과 댓글이 **한
청크로 그대로 합쳐집니다**.

실제로 "퇴근버스"라는 게시글(본문은 "야르" 한 단어)에 대출 광고 스팸 댓글
(`⭐ 라. 인 : King 365 z ⭐` 등)이 붙어서, 합쳐진 청크가 우연히 길이 필터(30자)를 통과해
버리는 걸 확인했습니다 — 실질 정보량은 여전히 "야르" 한 단어뿐인데 노이즈(스팸)가 길이만
부풀려서 필터를 속인 셈입니다.

**제안**: 문서 전체 길이와 무관하게, 본문과 댓글을 **항상 별도 청크로 분리**하거나 최소한
`content_type: body|comment` 필드로 구분해서 저장. 그러면 "본문 자체의 정보량"을 길이 필터가
정확히 평가할 수 있습니다.

### 2.3 스팸/광고성 텍스트가 `cleaner.py`를 통과함

`cleaner.py`는 URL/이메일/전화번호는 마스킹하지만(`_URL_RE`, `_EMAIL_RE`, `_PHONE_RE`),
`⭐ 라. 인 : King 365 z ⭐`, `사/고-자 신/불/자 연/체/자 가능` 같은 **대출/도박 스팸 특유의
패턴(전각/반각 혼용, 특수문자로 글자 사이 끊기, 대출 관련 은어)**은 안 걸러집니다. 전화번호
정규식이 있어도 이런 스팸은 전화번호를 텔레그램 아이디(`King 365z`)로 대체해서 우회하기 때문에
안 잡힙니다.

**제안**: 반복되는 스팸 특수문자 패턴(`⭐`, `/`, 공백으로 글자 쪼개기 등)이나 도박/대출 은어
블랙리스트를 기반으로 한 스팸 라인 제거 규칙 추가.

### 2.4 임베디드 JSON/메타데이터 조각이 본문에 섞임

네이버 블로그 청크 중 하나에서 `{"title":"신조어 야르 뜻 의미 10대 사이 유행단어","source":"`
같은 **깨진 JSON 조각**이 본문 텍스트 중간에 그대로 들어있는 걸 발견했습니다. 페이지의
공유 위젯/메타 태그(JSON-LD 등)가 본문 추출 시 같이 딸려온 것으로 보입니다.

**제안**: 본문 추출 후 `{"..."..}` 형태의 JSON 유사 패턴을 정규식으로 탐지해 제거하는 후처리 추가.

### 2.5 사이트 UI 상투어가 본문에 섞임

"본문 바로가기", "이웃추가", "공유하기 URL복사 신고하기", "찬반대결 책갈피 최신순-추천순" 같은
**사이트 공통 UI 텍스트**가 본문 크롤링 시 같이 긁혀 들어오는 사례가 여러 소스(네이트판,
네이버블로그)에서 확인됐습니다. `cleaner.py`는 이런 상투어를 다루지 않습니다.

**제안**: 소스별로 자주 나타나는 UI 상투어 목록을 만들어 `cleaner.py`에 라인 단위 제거 규칙으로
추가. 또는 크롤러의 본문 선택자(CSS selector)를 더 좁혀서 애초에 이런 영역이 안 잡히게.

## 3. 임베딩/저장 — `embedding/pipeline.py`

### 3.1 콘텐츠 품질 필드가 payload에 없음

지금 RAG 쪽(`analysis/rag_pipeline.py`)이 매 쿼리마다 `len(text.strip()) < min_length`,
`keyword in text/title` 같은 검증을 그때그때 재계산합니다. 이건 매 검색 호출마다 반복되는
연산이고, 코드가 여러 군데(노트북 8/9번 셀, `rag_pipeline.py`)에 중복돼 있습니다.

**제안**: 임베딩(또는 전처리) 시점에 `char_count`, `contains_keyword_literal` 같은 필드를
미리 계산해서 payload에 저장. RAG 쪽은 이 필드를 그냥 필터 조건으로 쓰면 되고, 계산 로직이
한 곳(적재 파이프라인)에만 있으면 됩니다.

### 3.2 근접 중복 사전 제거가 없음

2.2/네이버 블로그 미러링에서 다룬 것처럼, 내용이 사실상 같은 문서가 여러 개 Qdrant에 들어갈 수
있습니다. 지금은 RAG 쪽에서 매 검색마다 `difflib`로 근접 중복을 걸러내고 있는데(연산 비용 있고,
완전한 해법도 아님), **적재 시점에 한 번만 걸러지면 그 이후 모든 쿼리가 혜택을 봅니다**.

**제안**: 임베딩 전에 콘텐츠 해시(SimHash/MinHash 등) 기반으로 기존에 저장된 것과 근접 중복인
문서는 건너뛰는 로직 추가.

### 3.3 `keyword` 태그 검증 게이트가 적재 시점에 없음

`docs/crawler-contamination-findings.md`에서 이미 다뤘듯, `keyword` 필드는 크롤러가 매긴
태그일 뿐 실제 내용과 일치를 보장하지 않습니다. 지금 RAG 쪽에서 하는 "title/text에 실제로
키워드가 있는지" 검증을, **임베딩 적재 시점으로 옮기면** 애초에 나쁜 데이터가 Qdrant에 안
쌓입니다 (저장공간도 절약되고, 모든 쿼리가 자동으로 깨끗한 데이터를 받음).

## 우선순위 제안

1. **청킹 최소 길이 상향(2.1)** — 코드 한 줄, 가장 빠른 효과
2. **본문/댓글 항상 분리(2.2)** — 스팸 댓글이 길이 필터를 속이는 문제의 근본 해결
3. **keyword 태그 검증을 적재 시점으로 이동(3.3)** — RAG 쪽 임시방편을 근본 해결로 전환
4. **네이버 블로그 미러링/근접중복 사전 제거(1.2, 3.2)** — 컨텍스트 낭비 방지
5. **스팸/UI 상투어 제거(2.3, 2.5), JSON 조각 제거(2.4)** — 데이터 품질 다듬기
6. **tavily 쿼리 설계 재검토(1.1)** — 가장 판단이 필요한 부분 (쿼리를 바꾸면 수집량 자체가
   달라질 수 있어 신중한 검토 필요)
7. **리다이렉트/스니펫 URL 감지(1.3)** — 발생 빈도가 낮아 보여 우선순위 낮음

## 참고: RAG 쪽에서 임시로 넣은 방어책 (요약)

근본 해결 전까지 `analysis/rag_pipeline.py`의 `search_relevant_chunks`에 넣어둔 것들 —
위 개선이 이뤄지면 이 코드들의 부담이 줄어들거나 단순화될 수 있습니다:
- 최소 길이 필터, title/text 키워드 하드필터(공백·물결표 정규화)
- dense 코사인 유사도 하한선
- 소스당 최대 개수 제한(facet 단위 + 병합 단위)
- `difflib` 기반 근접 중복 제거
- 프롬프트에 소스 신뢰도 위계(1차/2차 자료) 구분 지시
