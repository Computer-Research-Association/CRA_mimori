# 크롤링 데이터 오염(키워드-내용 불일치) 조사 정리

RAG 답변 품질 실험(`analysis/langchain_playground.ipynb`, feature/lang_hi) 중 검색 결과에서 발견한 문제와,
코드 추적으로 확인한 원인 추정 내용입니다. 크롤러 코드 자체는 건드리지 않았고, 데이터 흐름만 따라가봤습니다.

## 문제 요약

Qdrant에 저장된 청크는 `keyword` 필드(어떤 검색 작업으로 수집됐는지 크롤러가 매긴 태그)와,
`title`/`text`(실제로 그 문서에 있는 내용)가 서로 독립적인 값입니다. 둘이 항상 일치해야 한다는
검증이 파이프라인 어디에도 없어서, 크롤러가 엉뚱한 글을 수집하면 `keyword="A"`인데 내용은 전혀
다른 주제인 문서가 그대로 저장됩니다.

## 구체적 사례

### 사례 1: `keyword="거제야호"`인데 완전히 무관한 문서

- `눈으로 보는 괌자유여행정보` (pann.nate.com/talk/114796949)
- `#1. 백설아이 in TaiWan` (pann.nate.com/talk/119590041)
- `앙팡) 시크한 엄마의 요절복통 에피소드` (pann.nate.com/talk/310866560)

이 중 앞의 둘은 게시글 번호가 실제 관련 문서들(375xxxxxxx대)보다 훨씬 낮습니다 — 네이트판 글
번호는 순차 발급이라, 이 두 문서는 "거제야호"라는 밈이 생기기 한참 전에 작성된 오래된 글로 보입니다.

또한 이 문서들의 `text` 내용을 보면 실제 게시글 본문이 아니라 "찬반대결/책갈피/최신순-추천순"
같은 **사이트 UI·사이드바 텍스트가 섞여 들어가 있습니다** — 정상적인 본문 추출이 안 된 흔적입니다.

### 사례 2: `keyword="야르"`에서 완전히 무관한 갤러리의 한 줄짜리 게시글

`lotto_new2`, `projectnike`, `hle`, `bser`, `zenless_zone_zero`, `streetfighter` 등 서로 전혀
무관한 디시인사이드 갤러리에서, 본문이 그냥 `"야르"` 한 단어(+ `- dc official App`)뿐인 게시글이
다수 수집됨. "야르"가 이미 범용 감탄사로 쓰이다 보니, 그 단어가 들어간 글이면 갤러리 주제와
무관하게 다 걸린 것으로 보입니다.

## 원인 추정 (코드 근거)

### 1. 사이트 자체 검색 결과를 무검증으로 신뢰

- `crawlers/natepann_crawler.py`의 `_get_post_urls()`: `pann.nate.com/search/talk?q={키워드}`
  (네이트판 자체 통합검색)에 검색어를 던지고, 결과로 나온 URL을 그대로 방문합니다.
- `crawlers/dcinside_crawler.py`의 `_get_post_urls()`: `search.dcinside.com/post/q/{키워드}`
  (디시인사이드 **갤러리 전체를 대상으로 하는 통합검색**)도 동일한 구조입니다.
- 두 경우 다, 검색엔진이 반환한 글이 실제로 그 키워드를 다루는 글인지 확인하는 로직이 없고,
  날짜 컷오프 외에는 필터가 없습니다. 검색엔진 자체가 완전 정확도 매칭이 아니라면(토큰 일부
  일치, 관련어 확장 등) 무관한 글이 결과에 섞여도 그대로 수집됩니다.

### 2. 날짜 필터의 "파싱 실패 → 최근 글로 간주" 폴백 구멍

두 크롤러 모두 동일한 패턴입니다 (`natepann_crawler.py` `_parse_search_date`,
`dcinside_crawler.py` `_parse_search_date`):

```python
if pub_date and pub_date < cutoff:
    old_skipped += 1
    continue
```

`pub_date`가 `None`(날짜 파싱 실패)이면 `if pub_date and ...`가 거짓이 되어 **날짜 필터를
그냥 건너뛰고 무조건 수집**합니다. 의도한 목적은 "오늘 작성된 글은 시각만 표시되어 날짜
포맷 파싱이 실패하는 경우 최근 글로 간주"인데, **그 외 다른 이유로 파싱이 실패하는 모든
경우도 똑같이 '최근 글'로 오인되어 컷오프를 우회**합니다. 오래된 글이 실제로 이 경로로
새어 들어왔는지는 확인 못 했지만, 사례 1의 문서들이 오래된 글로 추정되는 점과 맞아떨어지는
구조적 구멍입니다.

### 3. (추정) 오래된 페이지의 HTML 구조 변화로 인한 본문 추출 실패

사례 1 문서들의 `text`에 사이트 UI 텍스트(찬반대결/책갈피 등)가 섞여 있는 것은, 크롤러의
CSS 셀렉터(`div.post-tit-info`, `div.posting` 등)가 최신 페이지 구조 기준으로 짜여 있어서,
오래된 글의 (아마도 다른) HTML 구조에서는 의도한 본문 대신 사이드바/위젯 영역을 잘못
긁어온 것일 수 있습니다. 확인 필요.

## 제안하는 개선 방향 (우선순위 순)

1. **검색 결과 → 실제 저장 사이의 관련성 검증 추가**: 최소한 게시글 제목 또는 본문에 검색
   키워드(또는 핵심 토큰)가 실제로 포함돼 있는지 확인 후 저장. 지금은 검색엔진이 반환했다는
   사실만으로 신뢰하고 있습니다.
2. **날짜 파싱 실패 시 "최근 글로 간주"하는 폴백 재검토**: 정말 오늘 글인지와 그냥 파싱
   실패인지 구분이 안 되는 지금 로직 대신, 파싱 실패를 명시적으로 로그로 남기거나 별도
   처리하는 걸 고려.
3. **오래된 글 HTML 구조 확인**: 사례 1 URL(114796949, 119590041) 실제로 열어서, 지금
   셀렉터가 그 페이지에서 뭘 긁어오는지 확인.

## 참고: RAG 쪽에서 임시로 넣은 방어책

크롤러를 고치기 전까지, 검색/분석 쪽(`analysis/rag_pipeline.py`, `search_relevant_chunks`)에서
아래 방어 로직을 추가했습니다 (근본 해결은 아니고 증상 완화용):
- 청크의 `title`/`text`(공백 제거 후) 어디에도 키워드 문자열이 없으면 하드 필터로 제외
- 텍스트 길이가 너무 짧은(기본 30자 미만, `min_length` 파라미터) 청크 제외
- 필터로 줄어들 걸 감안해 `top_k * over_fetch_factor`개까지 넉넉히 받아온 뒤 필터링,
  통과작이 `top_k`보다 적으면 탈락작으로 백필

## 크롤러 쪽을 고칠 때 같이 확인해주면 좋은 것 (RAG 쪽 코드의 전제)

위 방어 로직들이 지금 크롤러/전처리 코드의 특정 동작에 암묵적으로 기대고 있어서, 크롤러 쪽을
바꿀 때 아래 사항들도 같이 봐주시면 좋겠습니다. 에러가 나는 건 아니고(전부 `.get()`으로 안전하게
접근), **조용히 무력화되거나 조용히 오작동하는 종류**라 놓치기 쉽습니다.

1. **관련성 검증(개선안 1번)을 넣으면 → RAG 쪽 키워드 하드필터는 자연히 no-op이 됨.**
   해로운 건 아니라 급히 지울 필요는 없지만, 참고로 알아두시면 좋습니다. (반대로 `min_length`
   필터는 "관련성"이 아니라 "정보량" 문제라 계속 유효합니다 — 짧은 감탄사성 게시글은 관련성
   검증을 통과해도 여전히 존재할 수 있음.)

2. **`title` 필드의 의미가 바뀌면 → 나무위키 롱폼 문서 보호가 조용히 깨짐.**
   지금 `preprocessing/chunker.py`가 나무위키 문서의 **모든 청크에 부모 문서 제목을 그대로
   복사**해서 넣어주는 덕분에, 특정 섹션 본문에 키워드가 없어도 title 체크로 RAG 필터를
   통과합니다. `title` 필드를 다른 용도(예: 섹션 제목)로 바꾸는 리팩터링을 하신다면, 이
   보호가 소리 없이 사라진다는 점 감안해주세요.

3. **payload 필드명이 바뀌면 → 전부 백필로 새는데 티가 안 남.**
   `keyword`/`title`/`text` 같은 필드명을 리팩터링하시면, RAG 쪽은 에러 없이 그냥 모든
   청크를 "빈 문자열"로 읽어서 길이 필터에 다 걸리고, 매번 탈락작 백필만 발생하는 상태가
   됩니다. 필드명 변경이 있으면 꼭 저희 쪽(`analysis/rag_pipeline.py`)에도 알려주세요.

4. **참고로, `SOURCES`에서 tavily/youtube만 제외하는 지금 설정은 이미 근거가 약합니다.**
   원래 "tavily/youtube가 오염 주범"이라는 가정이었는데, 이번 조사로 dcinside/natepann도
   같은 구조적 버그(사이트 검색 무검증 신뢰)를 갖고 있는 걸 확인했습니다. 크롤러 개선과
   별개로, 소스 필터링 전략 자체를 다시 봐야 할 수도 있습니다.

이 문서는 특정 시점의 코드를 그대로 인용한 스냅샷입니다 — 위 개선 사항들을 반영하신 뒤에는
문서 속 코드 인용부가 낡은 정보가 될 수 있으니, "현재 상태"가 아니라 "그 당시 발견 기록"으로
참고해주세요.
